# work-agent

Slack에서 요청하고, 로컬 웹페이지에서 업무를 조회하며, Jira에 워크로그를 등록하는 개인 업무 에이전트입니다. Java 21과 SQLite로 실행하며, 각자 에이전트 이름을 정해 사용할 수 있습니다.

## 준비 사항

업무 글쓰기 스킬과 Claude 출력 스타일의 설치·업데이트·평가는 [글쓰기 설치 안내](docs/writing-installation.md)를 참고하세요. 공통 기준과 `write-message`, `write-document`를 저장소에서 함께 관리합니다.

- Java 21 이상과 Maven이 필요합니다.
- 자연어 요청을 사용하려면 Codex CLI 또는 Claude Code CLI를 설치하고 로그인해야 합니다.
- Slack, Jira, 캘린더는 사용할 기능에 맞춰 연결합니다. 연결하지 않아도 로컬 화면에서 할 일과 계획을 관리할 수 있습니다.

## 실행

저장소를 복제하고 개인 설정 파일을 준비하세요.

```powershell
git clone https://github.com/hwangkyungha/work-agent.git
cd work-agent
Copy-Item config.example.properties config.properties
```

`config.properties`를 편집한 뒤 다음 명령으로 실행하세요.

```powershell
./start.ps1
```

첫 실행 시 테스트와 빌드를 수행합니다. 브라우저에서 [work-agent](http://127.0.0.1:8765)을 여세요. 기본적으로 이 PC에서만 접속할 수 있습니다. 자동 복구까지 멈추려면 `./stop.ps1`을 실행하세요. 다시 시작할 때는 `./start.ps1` 또는 `./start.ps1 -Background`를 직접 실행하세요.

소스를 수정했으면 실행 중인 프로그램을 종료한 뒤 `./build.ps1`로 테스트하고 다시 빌드하세요. 빌드에는 Maven과 의존성을 내려받을 인터넷 연결이 필요합니다.

Windows에서 로그인 시 자동 실행하고 종료 후 자동으로 다시 켜려면 `./install-startup.ps1`을 한 번 실행하세요. 현재 사용자 계정으로 `WorkAgent-Recovery` 예약 작업을 등록합니다. 이미 포트에서 프로그램이 실행 중이면 중복으로 켜지 않습니다. 창 없이 실행할 때 로그는 `work/logs`에 남습니다. `./stop.ps1`은 중지 상태를 파일로 남겨 예약 작업의 자동 복구도 막습니다. 직접 시작하기 전까지 중지 상태를 유지합니다. 자동 실행 등록 자체를 해제하려면 Windows 작업 스케줄러에서 해당 작업을 사용 안 함으로 바꾸세요.

## 연결 설정

`config.example.properties`를 복사한 `config.properties`에 개인 설정을 입력하세요. 같은 이름의 환경 변수 값이 우선합니다. Windows 파일 경로에는 `/`를 사용하세요. `config.properties`와 업무 데이터는 Git에 포함되지 않습니다.

### 내 에이전트 이름

저장소와 제품 이름은 `work-agent`입니다. 사용자는 로컬 `config.properties`에서 자신의 에이전트 이름과 부르는 말을 정할 수 있습니다.

```properties
AGENT_NAME=work-agent
AGENT_CALL_NAME=work-agent
```

`AGENT_NAME`은 화면과 대화에서 사용할 이름이고, `AGENT_CALL_NAME`은 요청 앞에서 부르는 말입니다. 예를 들어 이름을 `보리`, 부르는 말을 `보리야`로 정하면 `보리야, 브리핑`이라고 요청할 수 있습니다. 이름 없이 `브리핑`이라고 요청해도 동작합니다. 부르는 말만 입력하면 에이전트가 응답합니다. 변경 후에는 서버를 다시 실행하세요.

개인 이름은 로컬 설정에만 저장합니다. 공유용 예제 설정과 Slack 앱 manifest의 기본 이름은 `work-agent`입니다. Slack에 보이는 봇 이름도 바꾸려면 앱 생성 시 manifest의 `display_information.name`과 `features.bot_user.display_name`을 원하는 이름으로 변경하세요. 이미 만든 Slack 앱의 표시 이름은 Slack 앱 설정에서 변경해야 합니다.

### Slack

1. [Slack 앱 만들기](https://api.slack.com/apps)에서 **From a manifest**를 선택하고 `slack-app-manifest.json`을 입력하세요.
2. 앱을 사용할 워크스페이스에 설치하고 Bot User OAuth Token을 `SLACK_BOT_TOKEN`에 넣으세요.
3. Basic Information → App-Level Tokens에서 `connections:write` 권한을 가진 토큰을 만들고 `SLACK_APP_TOKEN`에 넣으세요.
4. 본인의 Slack 프로필에서 멤버 ID를 복사해 `SLACK_USER_ID`에 넣으세요.
5. 앱을 실행하고 봇에게 DM을 보내세요. 지정한 본인의 DM만 처리합니다.

공개 수신 주소 없이 Socket Mode로 연결합니다. 초기 버전은 개인용이며 공용 채널의 멘션이나 여러 사용자의 업무 분리를 지원하지 않습니다.

Slack 요청 메시지에는 처리 중 모래시계, 성공 시 체크, 실패 시 X 반응을 붙입니다. 이미 설치한 Slack 앱에 `reactions:write`가 없으면 봇 권한에 추가하고 앱을 다시 설치하세요.

만료되는 app-level 토큰(`xoxe.xapp-`)을 사용한다면 `SLACK_REFRESH_TOKEN`, `SLACK_CLIENT_ID`, `SLACK_CLIENT_SECRET`, `SLACK_APP_TOKEN_EXPIRES_AT`도 설정하세요. 만료 시각은 밀리초 단위 Unix 시간입니다. 만료 1시간 전에 토큰을 갱신하며, 갱신된 access/refresh 토큰 쌍은 개인 SQLite 데이터베이스에 함께 저장하여 재시작 후에도 사용합니다. 만료가 없는 `xapp-` 토큰에는 이 설정이 필요 없습니다. 같은 갱신 토큰을 사용하는 다른 봇은 이전 전에 종료해야 합니다. [Slack 공식 안내](https://docs.slack.dev/authentication/using-token-rotation/)

`CLAUDE_SESSION_TIME=06:00` 또는 `CODEX_SESSION_TIME=06:00`을 설정하면 주말을 포함해 매일 한국 시간 오전 6시에 해당 CLI에서 임시 세션을 열어 짧은 질문을 보내고, 성공 여부를 본인 Slack DM으로 알립니다. 각 예약은 업무에 사용하는 `AGENT_ENGINE`과 별도로 동작하며, 값을 비우면 꺼집니다. 필요한 경우 `CLAUDE_EXECUTABLE`에 Claude 실행 파일 경로를 지정하세요. 실패하면 그날은 다시 호출하지 않으며, 예정 시각에서 한 시간이 지난 뒤 프로그램을 켜면 그날 요청을 생략합니다.

### Jira

`JIRA_EMAIL`에 자신의 Atlassian 계정 이메일을 입력하고, `JIRA_API_TOKEN` 환경변수에 API 토큰을 설정하세요. `JIRA_TOKEN_ENV=JIRA_API_TOKEN`은 토큰을 읽을 환경변수 이름을 지정합니다. 토큰 값을 설정 파일에 복사하지 않습니다. 지정한 환경변수가 비어 있어도 다른 토큰으로 대체하지 않습니다.

scope가 있는 Cloud 토큰은 `JIRA_KIND=cloud`로 설정하고, `JIRA_URL`에 `https://api.atlassian.com/ex/jira/{cloudId}`를 입력하세요. Cloud ID는 자신의 Jira 사이트의 `https://<사이트>.atlassian.net/_edge/tenant_info`에서 확인할 수 있습니다. Classic scope는 `read:jira-work`, `write:jira-work`, `read:jira-user`를 사용합니다. 토큰 scope와 별도로 자신의 Jira 계정에도 이슈 조회와 워크로그 등록 권한이 있어야 합니다.

`start.ps1`은 Windows 사용자 변수의 `JIRA_API_TOKEN`을 실행할 Java 프로세스에 전달하므로, 이미 열려 있는 Codex나 터미널에서도 새 사용자 변수를 사용할 수 있습니다.

| 설정 | 내용 |
|---|---|
| `JIRA_URL` | scope가 있는 Cloud 토큰은 `https://api.atlassian.com/ex/jira/{cloudId}`, 그 외에는 Jira 기본 주소입니다. |
| `JIRA_SITE_URL` | 선택 항목입니다. 이슈 링크에 사용할 사이트 주소이며, 비우면 Jira에서 확인합니다. |
| `JIRA_KIND` | Cloud는 `cloud`, 사내 Jira Data Center는 `server`입니다. |
| `JIRA_TOKEN_ENV` | 토큰 값을 읽을 환경변수 이름입니다. 현재 `JIRA_API_TOKEN`을 사용합니다. |
| `JIRA_EMAIL` | Cloud API token을 사용할 때 계정 이메일을 넣습니다. 비우면 Bearer 인증을 사용합니다. |
| `JIRA_JQL` | 내 업무를 가져올 검색 조건입니다. 기본값은 내 담당 미해결 이슈와 최근 수정 이슈입니다. |

워크로그는 인증한 계정으로 등록합니다. Jira의 시간 추적 기능과 해당 이슈에 시간을 등록할 권한이 필요합니다. 이슈별 시간을 `3h`, `2.5h`, `2h 30m`처럼 입력합니다. 하루 합계를 8시간으로 제한하지 않으며, 작업 근거에 없는 회의 이슈도 직접 추가할 수 있습니다. 메시지 수를 근무 시간으로 환산하지 않습니다.

등록 중 응답을 받지 못하면 결과를 **확인 필요**로 남깁니다. 재요청할 때 추적 문구가 있는 기존 Jira 기록을 찾아 중복 등록을 피합니다. 기존 등록을 확인하지 못하면 재등록하지 않습니다. 이 경우 Jira 기록을 직접 확인해야 합니다. 등록된 항목은 보존하면서 다른 이슈의 시간을 추가할 수 있습니다. 이미 등록된 항목의 수정과 삭제는 지원하지 않습니다. 기존 비율 초안은 저장된 초 단위를 그대로 시간 입력으로 보여줍니다.

이슈 번호를 누르면 Jira 이슈로 이동합니다. 로컬 업무 상태는 `todo`, `in-progress`, `done`이며, Jira에 연결된 업무는 현재 이슈에서 실제로 변경 가능한 상태를 보여줍니다. 프로젝트의 워크플로와 이슈 권한을 따르며, Jira에서 완료 범주인 상태로 바꾸면 완료 목록으로 이동합니다. 추가 필수 입력이 필요한 상태 변경은 Jira 페이지에서 처리하세요. **숨기기**는 내 목록에서만 제외하므로 Jira 상태와 담당자는 바뀌지 않으며, 다시 동기화해도 숨김을 유지합니다. 숨긴 일 목록에서 복원할 수 있습니다.

### Google Calendar

Google OAuth를 연결하면 일정 조회·등록·수정·삭제에 같은 캘린더를 사용합니다. 아래 회의실 예약 설정의 Google 연결을 그대로 사용하며, 회의실을 예약하지 않고 일정만 등록할 수도 있습니다. OAuth 연결 전에는 아래 ICS 주소로 읽기 전용 조회를 사용할 수 있습니다.

자신의 iCal 주소를 로컬 `config.properties`의 `CALENDAR_ICS_URL`에 입력하세요. 이 이름의 환경변수를 새로 만들 필요는 없습니다. 형식은 다음과 같습니다.

```properties
CALENDAR_ICS_URL=https://calendar.google.com/calendar/ical/캘린더주소/basic.ics
```

공개 주소가 외부에서 조회되지 않으면 같은 캘린더의 비공개 iCal 주소로 바꿀 수 있습니다. 비공개 주소를 사용하는 절차는 다음과 같습니다.

1. 컴퓨터에서 [Google Calendar](https://calendar.google.com)를 열고 설정으로 들어가세요.
2. 왼쪽의 **내 캘린더의 설정**에서 업무 일정을 관리하는 캘린더를 선택하세요.
3. **캘린더 통합**에서 **iCal 형식의 비공개 주소**를 복사하세요.
4. 이 주소를 로컬 `config.properties`의 `CALENDAR_ICS_URL`에 입력하고 프로그램을 다시 실행하세요. 비공개 주소는 채팅이나 공유 문서에 올리지 마세요.

비공개 주소가 보이지 않으면 조직 관리자가 제공을 제한했을 수 있습니다. 이 경우에는 관리자에게 확인하거나 Google Calendar API를 통한 계정 연결을 추가해야 합니다. [Google 공식 안내](https://support.google.com/calendar/answer/37648?hl=ko)

`CALENDAR_ICS_URL`에 구독용 ICS 주소를, 또는 `CALENDAR_ICS_FILE`에 내보낸 ICS 파일 경로를 넣으세요. 반복 일정, 제외 날짜, 개별 일정 변경과 취소를 반영합니다. 조회 범위는 오늘 기준 이전 14일부터 이후 60일까지입니다.

OAuth가 연결되면 ICS 대신 Google API로 조회합니다. Google 일정 ID를 기준으로 표시하고 수정·삭제하며, Google에서 삭제된 일정도 다음 동기화에 반영됩니다. 일정 자동 갱신은 5분 주기이고, 화면의 기록 새로 확인으로 즉시 갱신할 수 있습니다. 브리핑 전에는 최신 캘린더를 확인합니다.

### 회의실 예약

Windows에서 Java 21과 work-agent로 다우오피스 회의실을 조회·예약·취소합니다. 처음 한 번 브라우저를 설치하고 그룹웨어에 로그인하세요.

```powershell
./build.ps1
./groupware.ps1 setup
./groupware.ps1 login
./groupware.ps1 status
```

Slack 또는 업무 수첩의 대화창에 `호박아, 다음 주 월요일 오후 2시부터 3시까지 6명이 CI 리포트를 검토할 회의실을 예약해 줘`처럼 요청하세요. 조회만 하려면 `예약 가능한 회의실을 알려 줘`라고 요청하세요. 날짜·시작과 종료 시각이 빠졌으면 추가로 묻습니다. 인원 수는 수용 인원에 맞는 회의실을 고를 때만 사용합니다. `11-4 회의실을 예약해 줘`처럼 회의실을 지정하면 인원 수를 묻지 않습니다. 그룹웨어의 참석인원 명단에는 항상 `-`를 입력합니다. 시간은 모두 한국 시간이며 30분 단위입니다. 예약 가능한 요일은 그룹웨어의 회의실별 설정을 조회해 판단합니다. 빈 시간이 있어도 예약 불가 요일이면 이유를 안내하고 예약하지 않습니다. 회의실을 지정하지 않으면 설정된 우선순위로 선택하고, 우선순위 밖의 회의실만 남으면 선택을 요청합니다.

그룹웨어 설정은 `%LOCALAPPDATA%/Suresoft/groupware/settings.json`입니다. `baseUrl`, `rooms`, `preferredRooms`에서 그룹웨어 주소·회의실 수용 인원·우선순위를 조정합니다. 암호화 세션 `session.enc`와 중복 예약 방지 기록 `bookings.jsonl`도 같은 폴더에 저장합니다. 기본 위치를 바꾸려면 `GROUPWARE_CONFIG`에 설정 파일 경로를 지정하세요. 이 폴더에는 개인 로그인 정보가 있으므로 Git이나 부서 공유 데이터에 넣지 않습니다.

Google Calendar에도 등록하려면 Google Calendar API를 활성화하고, 데스크톱 앱 유형으로 만든 OAuth JSON을 공통 설정 폴더의 `google-client.json`에 저장하세요. `settings.json`의 `googleCalendarId`에는 등록할 캘린더 ID를 넣습니다. 기본값은 `primary`입니다.

```powershell
./groupware.ps1 calendar-login
./groupware.ps1 calendar-status
```

로그인한 계정에는 해당 캘린더의 일정 쓰기 권한이 필요합니다. OAuth 앱이 외부 사용자 대상 테스트 상태라면 로그인할 계정을 Google 인증 플랫폼의 대상(Audience) → 테스트 사용자에 먼저 추가하세요. Calendar 일정 조회·수정 권한을 승인하면 갱신 토큰은 `google-token.enc`에 Windows 사용자별로 암호화해 저장합니다. Google의 테스트 상태 앱은 갱신 토큰의 유효기간이 제한될 수 있으므로, 계속 사용할 때는 Google의 게시 상태와 조직 사용 정책을 확인하세요.

예약 번호를 다시 조회해 확인한 뒤에만 예약 완료로 안내합니다. 예약은 성공하고 캘린더 등록만 실패했다면 예약을 유지하고 원인을 알려줍니다. 같은 예약을 다시 요청하면 회의실을 추가 예약하지 않고 캘린더 등록을 다시 시도합니다. 예약 제출 뒤 결과를 확인하지 못한 경우에는 추가 예약을 막고 그룹웨어 내역을 확인하도록 안내합니다. 세션이 만료되면 `./groupware.ps1 login`으로 다시 로그인하세요. 비밀번호와 보안문자는 저장하지 않습니다.

### 자연어 처리

기본값은 이미 로그인한 `codex` CLI입니다. `AGENT_ENGINE=claude`로 바꾸면 Claude CLI를 사용합니다. CLI 실행 파일을 찾지 못하면 `AGENT_EXECUTABLE`에 실행 파일 경로를 넣으세요. Windows의 npm Codex 설치는 `node`와 Codex 진입 스크립트를 통해 실행합니다.

Codex는 사용자 도구 설정을 읽지 않는 별도의 일회성 세션을 사용합니다. 사용자 설정에 있는 전용 모델 제공자나 프록시 설정은 그대로 상속하지 않습니다. Claude는 내장 도구와 MCP를 꺼 두고 요청을 해석합니다. 프로그램이 허용한 작업만 검증해 실행하며, AI가 임의 명령을 실행하지 않습니다. `AGENT_MODEL`을 비워 두면 CLI 기본 모델을 사용합니다.

`AGENT_ENGINE=off`로 두어도 웹페이지의 업무·계획·기록·워크로그 기능을 쓸 수 있습니다. `브리핑`, `데일리`, `이번 주 워크로그`라는 간단한 조회 요청도 AI 호출 없이 동작합니다. 자연어 처리는 해당 CLI 계정의 사용량을 소비합니다.

## 사용할 수 있는 기능

- **업무 글쓰기:** 응답·후속 작업 설명·PR 리뷰 댓글에 실행 파일에 포함된 글쓰기 기준을 적용합니다. 사용자의 CLI 전역 설정이나 개인 스킬 설치에 의존하지 않습니다. 조건·부정·수치·확신 정도를 보존하고, 확인된 사실과 추정을 구분합니다. 자세한 기준과 예시는 [업무 글 작성 기준](docs/writing-examples.md)에 있습니다.

- **데일리 브리핑:** 진행한 일에는 기준일에 계획했던 업무를 먼저 표시하고, 계획하지 않았던 업무는 Jira 동기화·조회로 확인된 이슈와 연결된 작업 세션에서 이슈 번호와 제목만 추가합니다. 번호 형식만 맞는 REQ-001 같은 샘플 요구사항은 포함하지 않습니다. 자동 검증 작업 폴더(.ct-verify·llm_judge)와 평가 전용 세션도 제외합니다. 계획과 세션에 같은 이슈가 있거나 여러 도구에서 작업한 경우 한 번만 표시하며, 에이전트 응답 본문은 포함하지 않습니다. 오늘 계획과 공유할 문제·도움 요청·결정할 사항도 모읍니다. 검토할 작업 결과·마감 현황·연결 확인 시간은 포함하지 않습니다. 월요일은 금요일을 기준으로 하고, 휴가·공휴일 등으로 계획과 작업 기록이 없으면 가장 최근에 계획이나 작업 기록이 있는 평일을 사용합니다. 참고한 날짜를 본문에 표시합니다. 작업 결과 검토는 오늘 화면에서 계속 확인할 수 있습니다.
- **오늘 할 일:** 날짜마다 직접 선택합니다. 진행 상태·마감·중요도·긴급도나 전날 계획만으로 자동 추가하지 않습니다. 목록 아래의 최근 진행 작업, 마감이 다가오는 일, 중요도/긴급도가 높은 일에서 버튼으로 추가하거나 직접 등록할 수 있습니다. 최근 진행 작업은 한국 시간 기준 어제부터 3일 전까지 Jira 이슈와 연결된 작업 세션이 있고 현재 In Progress인 업무입니다. 마감 후보는 오늘부터 7일 뒤까지이며, 중요·긴급 후보는 사용자가 해당 표시를 켠 업무입니다. 숨기거나 완료한 업무와 이미 오늘 선택한 업무는 추천에서 제외합니다. 여러 조건을 만족하는 업무는 여러 분류에 표시되며, 추가하면 모든 추천에서 빠집니다. 새 날짜에는 빈 목록에서 시작하며 이전 날짜의 계획은 보존합니다. 기존 버전에서 저장한 당일 목록은 유지하며, 목록 비우기로 다시 선택할 수 있습니다. 드래그 순서는 자동 저장하고 중요도·긴급도순, 마감일순, 생성일순 정렬도 제공합니다. 키보드에서는 손잡이에 초점을 두고 `Alt+위/아래`로 옮길 수 있습니다. 다른 곳에서 추가·변경된 업무도 화면에서 입력 중이 아닐 때 30초 간격으로 확인합니다.
- **전체 할 일:** Jira 이슈 번호의 접두사로 프로젝트를 필터하고 이슈 번호·업무 이름·묶음 이름으로 검색합니다. 표시된 업무를 전체 선택하거나 개별 선택해 오늘 할 일 추가·묶음 및 업무 성격 변경·숨기기를 일괄 처리할 수 있습니다. 오늘 추가는 기존 계획과 정렬을 유지하고 이미 포함된 업무·완료·숨김 항목은 제외합니다. Jira가 연결된 업무는 숨기고 직접 등록한 업무는 삭제합니다. 삭제 전에는 확인하며, 활동 기록과 워크로그는 보존합니다. 숨긴 Jira 업무는 다시 복원할 수 있습니다. 이슈 키를 누르면 Jira로 이동하고, 제목을 누르면 수정 창이 열립니다. 제목 오른쪽의 상태 버튼을 누르면 로컬 상태 또는 실제 Jira 전환을 선택할 수 있습니다. 숨기기·삭제는 각 행의 더보기 메뉴에 있습니다. 생성일 정렬은 Jira 업무의 원래 생성일과 로컬 업무를 등록한 날짜를 사용하며, 생성일을 모르는 기존 기록은 마지막에 표시합니다. 우선순위는 중요·긴급 모두 해당 → 긴급 → 중요 → 일반 순서이며, 같은 우선순위에서는 마감일이 빠른 일을 먼저 보여줍니다.
- **업무 묶음과 선행 작업:** 등록·수정 창에서 묶음 이름과 먼저 끝나야 하는 작업을 선택합니다. 전체 할 일에서 여러 업무를 선택하고 ‘묶음·성격 변경’으로 한꺼번에 분류할 수 있으며, ‘선택한 업무의 묶음 해제’를 누르면 묶음에서 제외합니다. Jira 상위 이슈는 기본 묶음으로, is blocked by·depends on 관계는 기본 선행 작업으로 가져옵니다. 직접 지정한 값은 Jira 재동기화 뒤에도 유지되며 이 설정으로 Jira 관계를 변경하지 않습니다. 전체 목록은 묶음 안에서 선행 작업을 먼저 표시하고, 완료 수·전체 수·필터로 표시된 수를 구분합니다. 선행 작업이 남으면 대기 안내를 표시하지만 상태나 오늘 계획을 자동으로 바꾸지 않습니다. 순환 관계는 저장할 수 없습니다. 오늘 화면은 직접 선택한 업무만 모으며, 묶음으로 보기를 끄면 전체 우선순위를 드래그로 조정할 수 있습니다. 묶음 보기에서는 같은 묶음 안에서 순서를 조정합니다. 숨긴 선행 작업도 대기 판단에 포함하고, 직접 등록한 선행 작업을 삭제하면 연결도 정리합니다.
- **작업 결과와 다음 할 일:** 생성 날짜와 관계없이 본인 명의의 모든 열린 Draft PR을 접근 가능한 Bitbucket 저장소에서 모읍니다. 아직 확인하지 않았거나 마지막 확인 이후 head가 바뀐 결과를 먼저 보여줍니다. PR 설명 요약과 근거가 있는 후속 작업을 같은 섹션에 보여주며, 직접 등록한 작업 결과도 함께 표시합니다. PR·head별 제안은 재사용하고, 오늘 할 일에는 사용자가 버튼으로 선택할 때만 추가합니다. 검토 작업은 로컬 할 일로 만들어 원래 Jira 이슈를 다시 열지 않습니다. 조회하지 못한 저장소는 빈 결과와 구분해 표시하며 ‘다시 정리’로 수동 갱신할 수 있습니다.
- **데일리 자료:** 브리핑과 같은 기준으로 진행한 일과 오늘 계획을 모읍니다. 발생한 문제·필요한 도움·결정할 사항·추가 공유를 따로 기록할 수 있으며, 빈 항목은 출력하지 않습니다. HTML 보고서를 열어 파일로 저장하거나 인쇄할 수 있습니다.
- **활동 기록:** 수동 입력과 Claude/Codex 기록을 함께 조회합니다. CLI 원본은 수정하지 않습니다.
- **워크로그:** 요일별로 Jira 이슈 또는 세션 이름으로 묶은 작업 근거와 사용자·응답 메시지 수를 확인하고, 이슈별 시간을 저장합니다. 화면을 열 때 마지막 확인이 5분 이상 지났으면 선택한 주의 Jira 워크로그를 자동으로 읽고, Jira 워크로그 동기화 버튼으로 다시 확인할 수 있습니다. 등록자와 한국 날짜를 기준으로 읽으므로 나에게 할당되지 않은 회의·지원 이슈도 포함합니다. 등록된 기록은 워크로그 ID로 중복을 제거해 읽기 전용으로 표시하며, Jira에서 수정·삭제하면 재동기화 뒤 반영됩니다. 등록 시간과 추가 입력 시간을 나눠 보여주고 합산합니다. 네트워크 오류가 발생하면 이전 조회 결과와 초안을 유지합니다. 즐겨찾기에 이슈 번호를 등록하거나 최근 기록한 이슈를 누르면 선택한 날짜의 입력 목록에 추가됩니다. 즐겨찾기는 전체 할 일과 별도로 관리하며, 최근 이슈는 로컬에서 확인한 최근 90일의 등록 기록 중 최신 20개입니다. 과거 주의 기록도 해당 주를 동기화하면 최근 이슈에 반영됩니다. 이미 등록한 같은 이슈에 시간을 추가할 때는 새 워크로그를 만들고 기존 등록분은 다시 전송하지 않습니다. 하루씩 또는 주말에 여러 날짜를 이어서 처리할 수 있습니다. 입력 중인 이슈 목록과 시간은 날짜별로 같은 브라우저에 임시 보관하므로 요일·화면 전환과 새로고침 뒤에도 유지됩니다. 초안 저장을 누르면 서버에 저장하며, 시간 없이 이슈 목록만 저장할 수도 있습니다. 시간 형식 오류는 해당 입력란 아래에 표시하고 합계는 숫자로 유지합니다. 시간 미정 항목이 남으면 Jira 등록을 막고, 이미 등록한 기록은 수정·삭제하지 않습니다. 실제 Jira 등록은 별도 요청이나 버튼으로 실행합니다.
- **팀원 기록:** 이름과 Jira 계정을 등록하고 관찰, 칭찬, 피드백과 후속 조치를 남깁니다. 고정 역할 필드는 사용하지 않습니다. 일반 브리핑과 데일리 자료에는 개인 관찰 내용을 넣지 않습니다.
- **팀 Jira 정리:** 팀원별 담당 이슈와 해당 주에 Jira에 등록된 시간을 조회합니다. 기록된 시간이 전체 근무 시간이라고 해석하거나 개인 평가를 자동으로 만들지 않습니다.
- **팀원 통계 질문:** 자연어로 기간과 이슈 범위를 지정해 담당 건수와 등록 시간을 조회합니다. 담당 이력과 조회 기간이 겹치는 고유 이슈를 세므로 현재 담당자가 바뀐 이슈도 포함합니다. 이유를 물으면 이슈 설명·댓글과 해당 기간의 관찰 기록을 참고하고 사실과 추정을 구분합니다. 설명은 현재 내용이며, 이유 분석은 등록 시간이 긴 상위 5개 이슈와 이슈별 최근 댓글 20개를 참고합니다. 시간과 건수는 전체 조회 결과를 집계하며, Jira 계정이 볼 수 있는 범위에 한정합니다. 미래 날짜는 오늘까지로 계산합니다.
- **실행 결과 접수:** 외부에서 실행한 작업 결과, 결과물 위치, 검증 결과를 받아 검토 전후를 구분합니다.


### CLI 기록 수집

기본적으로 사용자 폴더의 `.codex/sessions`와 `.claude/projects`에서 최근 14일에 수정된 JSONL 파일을 읽습니다. `CODEX_LOG_ROOT`, `CLAUDE_LOG_ROOT`, `IMPORT_DAYS`로 범위를 지정할 수 있습니다. 파일별 읽은 위치를 저장하고, 아직 기록 중인 마지막 줄은 다음 수집까지 기다립니다.

대화 본문 중 사용자와 AI의 일반 텍스트만 수집하며 내부 추론과 도구 결과는 수집하지 않습니다. 날짜와 세션별 마지막 AI 응답을 활동 후보로 표시합니다. 같은 날짜·세션에서 확인된 Jira 이슈가 하나일 때 연결합니다. 본문에 나온 요구사항 번호를 Jira 키로 확정하지 않으며, 확인되지 않은 번호는 후보로만 남깁니다. 여러 이슈가 등장하면 임의로 하나를 고르지 않습니다. Slack에서 활동을 이슈에 연결할 수 있습니다. 후보는 작업 완료나 검증 성공을 증명하지 않으며 사용자가 데일리와 워크로그를 만들 때 확인해야 합니다.

원본은 원래 위치에 남고, 검색에 필요한 발췌와 출처를 SQLite에 보관합니다. 현재 구현은 JSONL 형식의 로컬 기록을 지원합니다. Codex의 다른 저장 형식이나 클라우드에만 있는 세션은 별도 연결이 필요합니다. 자연어 요청 시에는 최근 활동, 업무 목록, 최근 대화가 설정한 CLI에 전달됩니다. 전체 원본과 개인 관찰 기록은 일반 계획 요청의 문맥에 넣지 않습니다.

### 정기 실행

매일 오전 8시에는 최근 근무일의 계획과 실제 활동, 이어서 할 일 후보, 미확인 Draft PR과 후속 제안을 Slack으로 정리해 보냅니다. 하루 한 번 발송하며 재시작 후에도 중복하지 않습니다. `DRAFT_REVIEW_TIME`의 기본값은 `08:00`이고 빈 값이면 자동 발송을 끕니다. 이 알림은 주말에도 실행하며, 오전 9시 데일리 브리핑의 휴가 제외 규칙과는 별개입니다.

프로그램이 켜져 있는 동안 CLI 기록과 Jira·캘린더는 각각 마지막 동기화에서 5분이 지나면 갱신합니다. 이 수집에는 AI 모델을 호출하지 않습니다. **기록 새로 확인**으로 언제든 수동 동기화할 수 있습니다. Slack 연결 설정이 있으면 월요일부터 금요일까지 오전 9시에 브리핑을 한 번 보냅니다. 발송 직전에 연결된 캘린더에서 휴가 여부를 확인하고 Jira와 CLI 기록을 갱신합니다. 갱신에 실패하면 5분 뒤부터 발송 가능 시간 안에서 다시 시도합니다.

`CALENDAR_OWNER_NAME`에 캘린더에서 사용하는 본인 이름을 설정하면, 해당 이름과 `휴가`·`연차`·`반차`가 함께 있는 날은 브리핑을 보내지 않습니다. 오전·오후 반차도 제외하고, 다른 사람의 휴가는 제외 사유로 사용하지 않습니다. 휴가 일정은 연결한 캘린더에서 읽으므로 캘린더 연결이 필요합니다. 금요일 오후 4시 30분에는 주간 워크로그 정리 자료를 보내고 오후 4시 이후 팀원별 Jira 정리도 수행합니다. `BRIEFING_TIME`과 `FRIDAY_REVIEW_TIME`은 바꿀 수 있고, 빈 값이면 해당 알림을 끕니다.

시간대는 설정 옵션 없이 **Asia/Seoul**로 고정합니다. 날짜별 기록, 이번 주 범위(월요일부터 일요일), 예약 알림과 Jira 작업 시작 날짜를 모두 한국 시간으로 계산합니다. 늦게 켜진 프로그램은 예정 시각에서 한 시간 이상 지난 알림을 뒤늦게 보내지 않습니다. 컴퓨터가 꺼져 있으면 수집과 알림도 멈춥니다.

## Bitbucket PR 리뷰와 댓글 답변

리뷰 지적에는 실제 발생 조건과 기대 결과, 코드가 만드는 결과, 사용자 영향과 수정 방향을 남깁니다. 관련 명세·호출부·테스트를 함께 대조하고, 반증에 필요한 파일이 빠졌으면 추가로 읽습니다. 확인할 수 없는 전제는 검토 한계로 남기며, Slack 완료 메시지에도 발견한 문제와 영향을 요약합니다.

PR 리뷰의 기본은 로컬 저장소와 연결된 작업 세션입니다. ‘저장소 연결’ 안의 ‘추가 외부 명세’는 프로젝트 밖의 계약 등을 함께 확인할 때만 사용하는 선택 설정입니다. 저장소마다 참고 위치를 한 번 연결할 수 있습니다. 로컬 경로만 수정하면 기존 외부 명세 연결은 유지합니다. Bitbucket 문서 파일 주소 또는 공개 계약 사이트의 폴더 절대 경로를 한 줄에 하나씩 최대 4개 입력하세요. Slack에서도 “workspace/repository 리뷰에는 이 명세들을 참고하도록 설정해 줘”와 함께 위치를 알려 줄 수 있습니다. 설정은 로컬 데이터베이스에 저장하며, 이후 새 head의 자동·수동 리뷰에 공통 적용합니다. 요청 한 번에만 쓸 문서는 ‘추가 외부 문서 · 이번 검토만’로 전달합니다.

공개 계약 사이트는 `index.html`이 가리키는 버전의 `version.json`과 `contracts/catalog.json`을 읽습니다. 관련 계약을 최대 2개 고르고 해당 게시본의 공통 계약도 함께 확인합니다. 파일 해시를 확인한 문서만 로컬 스냅샷으로 남기므로 NAS 게시본이 바뀌어도 당시 근거를 재확인할 수 있습니다. 접근 실패나 해시 불일치는 검토 한계에 표시합니다. 관련 저장소의 구현 코드 전체를 매번 AI에 보내지는 않습니다.

일반 리뷰는 PR 주소와 head를 기준으로 기존 이력을 재사용합니다. 병합 대상 브랜치나 참고 명세만 바뀌면 다시 리뷰하지 않습니다. 댓글 답변은 댓글 ID와 수정 이력을 기준으로 재사용합니다. 이미 알린 같은 결과는 서버 재시작 후에도 다시 알리지 않습니다. 실패한 작업은 정기 조회에서 무한 재시도하지 않으며, 화면에서 다시 검토하거나 명시적으로 강제 재검토를 요청할 수 있습니다.

개발 검증에는 `/api/reviews/request`에 `validation: true`를 전달하거나 Slack에서 검증용 실행임을 명시하세요. 검증 결과는 운영 리뷰 이력과 분리하며 Slack 완료 알림과 Bitbucket 초안 저장을 하지 않습니다. 같은 head를 의도적으로 다시 검증할 때도 이 방식을 사용합니다. 운영 리뷰의 강제 재검토는 `rerun: true`로 요청합니다.

서버가 실행 중이면 한국 시간 08:00부터 16:30까지 30분마다 Bitbucket에서 접근 가능한 모든 저장소를 확인합니다. 수동 조회는 언제든 실행할 수 있습니다. 조회에서 새로 발견한 리뷰 요청과 내 PR의 답변할 댓글은 이어서 AI 검토와 답변 생성을 시작합니다. 같은 head와 댓글에 대해 처리한 결과는 재사용합니다. 리뷰 화면의 자동 갱신에서도 펼쳐 둔 검토 범위·근거 항목은 유지합니다. 저장소 목록을 미리 등록할 필요는 없습니다. 토큰이 가리키는 계정을 본인으로 판단합니다.

`BITBUCKET_API_TOKEN` 사용자 환경변수와 `BITBUCKET_EMAIL`을 설정하세요. 이메일을 비우면 `JIRA_EMAIL`을 사용합니다. API 토큰에는 `read:user:bitbucket`, `read:workspace:bitbucket`, `read:repository:bitbucket`, `read:pullrequest:bitbucket` 권한이 필요합니다. 워크스페이스 자동 조회 권한이 없을 때는 `BITBUCKET_WORKSPACES`에 워크스페이스 이름을 쉼표로 지정할 수 있습니다. 이 경우 조회하지 못하는 범위를 화면에 표시합니다. `BITBUCKET_AUTO_REVIEW=false`이면 자동 조회를 끄고 직접 요청한 PR만 검토합니다.

웹의 **PR 리뷰**에서 PR 주소로 검토를 요청하고, 결과와 코드 근거를 확인하거나 댓글 초안을 편집할 수 있습니다. Slack에서도 “이 PR을 리뷰해 줘”와 함께 주소를 보내거나, “나에게 온 리뷰 요청을 확인해 줘”라고 요청할 수 있습니다. 내 PR의 특정 댓글에 답변하려면 PR 주소와 댓글 번호를 함께 알려 주세요. 작업을 마치면 Slack으로 알립니다.

자동으로 찾은 리뷰와 답변은 **Bitbucket 비공개 초안**으로 저장합니다. 직접 요청한 검토는 웹에서 내용을 확인한 뒤 **Bitbucket 비공개 초안 저장**을 누르세요. Bitbucket에서 최종 내용을 확인하고 리뷰를 제출해야 다른 사람에게 공개됩니다. 승인과 병합은 수행하지 않습니다. 댓글에는 AI가 작성했다는 표시와 각자 설정한 에이전트 이름을 붙입니다.

검토에는 PR 설명·댓글, 변경 전후 코드, 변경된 명세 문서와 저장소 루트의 지침을 사용합니다. 검토 시점의 커밋을 고정하고, 후보를 반박하는 두 번째 검토와 실제 코드 줄의 인용 검사를 통과한 지적만 남깁니다. 낮은 확신, 사소한 제안, 근거가 맞지 않는 지적과 이미 작성한 같은 위치의 AI 댓글은 제외합니다. 확실한 지적이나 답변 근거가 없으면 댓글을 쓰지 않습니다. 이 검사는 오탐을 줄이지만 결함 탐지와 판단의 정확성을 보장하지는 않습니다.

원격 PR의 코드와 문서는 설정한 AI CLI에 전달됩니다. 코드를 실행하거나 테스트하지 않으며, 변경하지 않은 전체 코드와 외부 시스템까지 검토하지는 않습니다. 큰 파일·바이너리·접근할 수 없는 자료 등은 화면에 검토 한계나 오류로 표시합니다. 커밋이 바뀌면 이전 결과를 저장하지 않습니다. 댓글 저장 응답이 끊기면 중복 전송 대신 Bitbucket의 저장 결과를 먼저 확인합니다.

공식 문서: [PR 댓글 API와 권한](https://developer.atlassian.com/cloud/bitbucket/rest/api-group-pullrequests/#api-repositories-workspace-repo-slug-pullrequests-pull-request-id-comments-post), [비공개 댓글과 리뷰 제출](https://support.atlassian.com/bitbucket-cloud/docs/review-code-in-a-pull-request/).

## 외부 작업 실행기 연결

이 버전은 실행 결과를 접수하고 검토 상태를 관리합니다. 개발 작업을 자율적으로 실행하거나 테스트 성공을 자체 확인하는 실행기는 포함하지 않습니다. 기존 Claude/Codex 작업을 마친 뒤 아래 API로 결과를 전달할 수 있습니다.

`config.properties`의 `WORK_AGENT_TOKEN`에 직접 정한 긴 문자열을 넣고 서버를 다시 시작하세요. 외부 실행기에서 환경 변수로 같은 값을 사용해 다음과 같이 호출할 수 있습니다.

```powershell
$taskBody = @{
    title = 'LCT CI report 수정'
    jiraKey = 'CT-123'
    result = '수정한 결과를 검토해야 합니다.'
    artifact = 'D:/Git/lct의 커밋 또는 결과물 위치'
    verification = '실행기가 실제 확인한 테스트 결과'
    reviewed = $false
} | ConvertTo-Json
Invoke-RestMethod -Method Post -Uri 'http://127.0.0.1:8765/api/jobs' `
    -Headers @{ 'X-Work-Agent-Token' = $env:WORK_AGENT_TOKEN } `
    -ContentType 'application/json; charset=utf-8' -Body ([Text.Encoding]::UTF8.GetBytes($taskBody))
```

## 계획과 실제 수행 기록

오늘 화면의 ‘어제 계획과 실제’는 최근 근무일에 계획한 업무와 직접 추가한 수행 내용부터 보여줍니다. 모든 세션을 기본 목록에 나열하지 않습니다. ‘수행한 일 추가’를 누르면 메시지 수가 많은 순서로 작업 기록 후보를 확인할 수 있고, 기존 할 일을 선택하거나 기록이 없는 업무를 직접 입력할 수도 있습니다. 선택한 업무는 해당 날짜의 진행 중·완료로 기록하며, 오늘 계획이나 Jira 상태를 자동으로 변경하지 않습니다. 빈 세션 제목은 확인한 사용자 메시지로 보완하고, 빈 제목으로 기존 작업명을 지우지 않습니다. 계획만 한 일은 브리핑의 ‘진행한 일’에 포함하지 않습니다. 수행 상태는 그날의 기록이며 Jira 업무 상태를 변경하지 않습니다. 완료·취소로 확인한 업무는 자동 추천에서 제외합니다. 이어서 할 일은 최근 날짜와 활동 시각 순으로 정렬하고 Jira 키에 이슈 링크를 표시합니다. Jira가 없는 활동은 제목으로 표시하고, 기존 업무에 연결하거나 새 업무로 등록할 수 있습니다. 계획의 최초 목록과 변경 시점의 업무 정보를 보관하므로 업무 중 추가·제외·우선순위 변경을 구분합니다. 이 기능을 설치하기 전에 덮어쓴 계획 이력은 복원할 수 없습니다.

워크로그는 확인한 수행 목록 중 진행·완료된 업무만 기본 후보로 사용합니다. 선택하지 않은 세션을 시간 입력란에 자동 추가하지 않습니다. 평가 실행 폴더에서 생성한 세션은 수집·추천에서 제외하며, 하네스 저장소 자체를 개발한 기록은 유지합니다. 빠진 업무는 워크로그의 ‘수행 내용 추가’에서 선택하거나 기존 즐겨찾기·이슈 입력으로 추가하세요. 이미 입력한 시간과 서버에 저장한 초안은 보존합니다. Jira가 없는 업무도 시간을 입력해 초안으로 보관할 수 있으며, Jira 등록 전에 이슈를 연결해야 합니다. 초안을 저장한 뒤 확인한 새 활동은 ‘추가로 확인한 활동’에서 시간을 잃지 않고 추가합니다. Jira에서 이미 확인한 등록 기록은 새 입력 목록에 자동으로 중복 추가하지 않습니다. 실제 근무 시간은 사용자가 입력하며 메시지 수에서 추정하지 않습니다.

Draft PR은 생성 날짜와 관계없이 내 모든 열린 초안을 추적합니다. 금요일에 만든 미확인 결과도 월요일에 남습니다. 확인 상태는 PR 주소와 head 커밋별로 저장하므로 확인한 PR은 기본 목록에서 접고, 코드가 바뀌면 다시 검토 대상으로 표시합니다. 확인한 PR에서 남은 후속 제안은 계속 표시하며, 할 일로 등록하거나 제안 제외로 정리할 수 있습니다. 같은 후속 작업은 head가 바뀌어도 등록·제외 상태를 유지합니다. 병합·종료하거나 Draft를 해제한 PR은 다음 정상 조회에서 제외합니다. 조회에 실패한 저장소의 기존 결과는 유지하고 오류를 표시합니다.

제품, 업무 묶음, 업무 성격은 Jira 상하위 구조와 별도로 관리할 수 있습니다. 전체 할 일의 ‘묶음·성격 변경’에서 묶음과 업무 성격을 각각 일괄 수정할 수 있습니다. 지정하지 않은 분류는 유지하고, 묶음 해제와 미분류 변경은 명시적으로 선택합니다. 전체 할 일에서 제품·성격·Jira 프로젝트로 필터하고 선택한 업무를 일괄 이동할 수 있습니다. 기존 Jira 부모는 사용자 지정 업무 묶음이 없을 때 초기 묶음으로 사용합니다.

## 프로젝트에서 PR 검토

`REPOSITORY_ROOT`에는 로컬 저장소들이 있는 상위 폴더를 지정합니다. PR의 Bitbucket 원격 주소와 일치하는 저장소를 찾아, `work/data/review-worktrees` 아래 해당 head의 별도 Git worktree를 준비합니다. 개발 중인 폴더의 브랜치와 미커밋 파일은 변경하지 않습니다. 자동 검색 결과가 여러 개이거나 찾지 못하면 ‘PR 리뷰 → 저장소 연결’에서 로컬 경로를 지정하세요. 로컬 저장소가 없으면 발췌 자료로 검토했다는 사실을 표시합니다.

프로젝트 검토에서는 파일을 탐색하는 도구를 사용하고, PR별 CLI 세션을 유지합니다. Claude에는 Read·Grep·Glob만 허용하고, Codex에는 읽기 전용 실행 정책을 적용합니다. 테스트를 실행하지 않으며, 테스트 코드나 기록을 읽은 것과 실행한 결과를 구분합니다. 외부 명세 설정과 코드 인용 검증은 그대로 적용합니다. ‘PR 이해하기’에는 결함 유무와 별개로 목적, 주요 흐름, 읽을 파일, 검증 자료와 남은 질문을 정리합니다.

내 PR의 댓글 답변에는 Jira 키와 저장소로 원래 작업 세션을 찾습니다. 하나로 결정할 수 없으면 원본 세션을 임의로 선택하지 않습니다. PR 카드의 ‘원래 작업 세션 연결’에서 직접 지정할 수 있습니다. 원본 대화에서 답변용 세션을 분기하므로 원본 작업 세션에 자동 질문을 삽입하지 않습니다. 이후 댓글과 후속 질문은 답변용 세션을 이어 쓰고 현재 head의 코드로 이전 판단을 확인합니다. 검증용 실행은 운영 대화와 분리합니다.

Codex에도 Jira 키를 세션 이름 앞에 붙이는 규칙을 설치하려면 다음 명령을 실행하세요. 기존 개인 지침을 보존하고 백업합니다. 이름 변경 도구가 없는 환경에서는 제목 변경을 생략합니다.

```powershell
./scripts/install-session-rules.ps1
```

기존 활동의 Jira 오분류를 정리할 때는 데이터베이스를 백업한 뒤 다음 명령을 실행하세요. 서버와 외부 동기화는 시작하지 않습니다.

```powershell
java -jar work-agent-0.4.2.jar --repair-activity-links
```


오늘 페이지는 오늘 할 일을 먼저 보여 줍니다. 그 아래 **계획과 실제**를 펼쳐 오늘·이전 근무일·원하는 날짜의 진행 중/완료/보류 등을 정리하고, 계획 밖에 수행한 일을 추가할 수 있습니다. 같은 기록이 해당 날짜의 워크로그 후보에 반영됩니다. 워크로그에서도 선택한 날짜의 계획과 실제를 수정할 수 있습니다. 수정한 수행 상태는 Jira 상태를 변경하지 않습니다. 작업 근거와 최근 기록한 이슈는 기본으로 접혀 있으며, 화면 갱신 중에는 사용자가 펼친 상태를 유지합니다.

업무 성격은 `config.properties`의 `WORK_TYPES`에서 쉼표로 구분해 편집합니다. 기본 목록은 기능, 버그 수정, 리뷰, 회의, 고객지원, 조사·설계, 테스트·검증, 품질·성능, 운영, 문서, 기타입니다. 제품과 업무 묶음은 별도 분류로 유지하고, 중요도·긴급도도 별도로 설정합니다. 예를 들어 `WORK_TYPES=기능,버그 수정,회의,고객지원,기타`로 줄일 수 있습니다. 서버를 다시 시작하면 등록·편집·일괄 변경·필터에 적용됩니다. 목록에서 뺀 성격도 기존 업무에서는 보존되며, 검색과 기존 값 유지가 가능합니다. 값을 비우면 미분류만 사용합니다.

기존 할 일을 고르는 선택창은 이슈 번호나 제목을 입력해 검색할 수 있습니다. 수행한 일 추가·활동과 업무 연결·활동 기록에서 같은 방식으로 사용하며, 방향키와 Enter로 선택하고 Esc로 검색 목록을 닫을 수 있습니다. 활동을 기존 업무에 연결할 때는 새 업무의 Jira 입력란을 숨기고, ‘새 업무로 등록’을 선택하면 다시 표시합니다.


같은 Jira 번호는 하나의 할 일에만 연결합니다. Jira 동기화 전에 로컬 할 일을 만들었거나, 수집된 Jira 업무에 나중에 로컬 할 일을 연결해도 원래 로컬 업무 ID를 유지해 합칩니다. 동일 번호로 새 할 일을 등록하면 기존 업무를 재사용합니다. 선행 작업·계획과 당시의 업무 이름·활동·세션·후속 제안·워크로그의 업무 연결을 옮기며, 기록한 날짜·시간·Jira 등록 ID와 워크로그 중복 등록 방지 표시는 유지합니다. 예전 업무 ID로 들어온 요청과 브라우저의 임시 워크로그도 새 연결을 사용합니다.

기존 중복은 서버 시작 때 정리합니다. 정리 전 SQLite 전체 백업을 데이터 폴더의 `backups/before-task-merge-*.db`에 만들고, 업무별 병합 내역과 이전 ID 연결도 DB에 남깁니다. 중요도·긴급도·숨김·업무 묶음·성격 또는 같은 날짜의 수행 상태가 충돌하면 해당 병합은 되돌리고 전체 할 일 화면에 확인할 내용을 표시합니다. 두 업무의 충돌 값을 확인해 일치시킨 뒤 다시 연결하면 합칠 수 있습니다. Jira 상태·마감일 등은 Jira 자료로 갱신합니다.


일정 원본은 Google Calendar입니다. Slack에서 ‘오늘 일정에 서현지 휴가를 종일로 등록해줘’처럼 요청하거나 오늘 화면의 ‘일정 등록’을 사용합니다. 일정 제목을 누르면 수정하고, 삭제 버튼은 Google 일정 삭제를 확인받은 뒤 실행합니다. 종일 일정은 시작일과 마지막 날(포함)을 입력하며, 시간 지정 일정은 시작·종료 시각을 모두 입력합니다. 시각을 임의로 배정하지 않습니다. 반복 일정은 선택한 날짜의 회차만 수정·삭제합니다. Google의 변경이 먼저 발생하면 다시 확인하도록 안내하고 덮어쓰지 않습니다. 응답을 받지 못한 등록 요청은 같은 요청 ID로 재시도해 중복 생성을 막습니다. [Google 일정 등록](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert), [일정 수정](https://developers.google.com/workspace/calendar/api/v3/reference/events/patch)

내부 일정 목록은 Google 조회 결과를 보관하는 캐시입니다. 갱신 실패 시 이전 조회 결과라는 안내를 표시합니다. 기존 로컬 전용 일정은 서버 시작 때 전체 DB를 데이터 폴더의 `backups/before-google-calendar-*.db`로 백업한 뒤 `retiredMeeting` 기록으로 옮겨 목록에서 제외합니다. Google에 이미 있는 같은 제목의 일정을 다시 만들거나 삭제하지 않습니다. Google 쓰기 권한이 없으면 읽기 전용으로 표시하며, 일반 일정의 로컬 저장 경로는 사용하지 않습니다.
