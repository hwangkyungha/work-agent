# 사람이 읽는 업무 글

응답, 제안의 이유, 공유 문서와 PR 리뷰 댓글에 적용한다. JSON 구조, 액션 이름, 코드와 인용은 그대로 유지한다.

- 결론이나 요청을 먼저 쓰고 판단에 필요한 이유를 뒤에 설명한다. 독자가 이미 아는 배경과 작성 과정을 반복하지 않는다.
- 대상과 동작을 분명히 적는다. 명사를 이어 붙여 줄이기보다 누가 어떤 조건에서 무엇을 하는지 문장으로 쓴다.
- 날짜, 수치와 단위, 제품명, 이슈 번호, URL, 부정 표현과 예외 조건을 보존한다. 문장 길이만 줄여 조건과 인과관계를 지우지 않는다.
- 코드와 자료로 확인한 사실은 단정해서 말한다. 추정은 추정이라고 쓰고, 확인하지 못한 것과 없는 것을 구분한다.
- 익숙한 기술 용어는 유지한다. 독자에게 낯선 용어는 처음 한 번만 짧게 설명한다. 낯선 단어와 명사형을 일괄 금지하거나 자동 치환하지 않는다.
- 설명은 완결된 문장으로 쓴다. 제목과 상태 값은 짧게 유지한다. 같은 글에서 말투와 용어를 통일한다.
- 짧은 답변에는 불필요한 제목·표·인사말을 덧붙이지 않는다. 비교에는 표, 독립된 항목에는 목록, 원인 설명에는 문단을 사용한다.
- 리뷰 댓글에는 발생 조건, 확인한 동작, 영향과 필요한 수정을 쓴다. 코드로 확인되지 않은 가능성을 실제 결함으로 단정하지 않는다. 독립된 문제는 나누고 같은 원인의 지적은 한 번만 쓴다.
- 검토 결과가 없으면 지적을 억지로 만들지 않는다. 변경의 크기와 댓글 수를 결함의 근거로 삼지 않는다.

출력 전에 원래 자료와 대조한다. 수치·날짜·조건·부정·요청과 확신 정도가 바뀌지 않았는지 확인하고, 본문만 읽어도 무엇을 해야 하는지 알 수 있도록 고친다.
